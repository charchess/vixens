# INDIBA agent platform - Phase 0 POC

This directory contains the production-shaped **Phase 0 vertical slice** for the
INDIBA agent platform qualified in architecture issue #3279.

The POC deliberately keeps Hermes agents `alwaysOn`, but exercises the main
architectural boundaries end to end: user authentication, authorization,
runtime reconciliation, LLM brokerage, persistent Hindsight memory, tenant
isolation and persistent databases.

## Phase 0 topology

```text
browser
  -> Traefik
  -> Authentik ForwardAuth
  -> INDIBA Portal/BFF
  -> Control Plane MVP
       -> OpenFGA
       -> platform_core PostgreSQL
       -> HermesRuntime CR
            -> Hermes Operator MVP
            -> Hermes always-on runtime
                 -> Memory Gateway POC -> hs-indiba -> Hindsight -> hindsight_indiba PostgreSQL
                 -> LLM Gateway MVP -> OpenRouter
```

OpenBao + External Secrets provide database/provider/runtime credentials. No
provider secret is committed to Git.

## GitOps conventions

This slice follows the existing Vixens deployment conventions:

- packaged third-party software is deployed through Helm from Argo CD;
- INDIBA-owned components and trust-boundary resources are native manifests
  managed with Kustomize;
- platform PostgreSQL uses CloudNativePG CRs;
- Hindsight's Phase 0 memory database is currently a tenant-local
  `pgvector/pgvector:pg17` StatefulSet because Hindsight requires pgvector and a
  CNPG-compatible pgvector image has not yet been qualified. This is a POC
  exception, not the target database lifecycle pattern.

Argo CD applications:

- `indiba-platform`: Kustomize/native INDIBA resources;
- `indiba-openfga`: OpenFGA Helm chart;
- `indiba-hindsight`: Hindsight Helm chart.

## Implemented workloads

### Portal/BFF

A replaceable Node bootstrap portal runs behind Traefik + Authentik ForwardAuth.
It exposes authenticated identity and `Mes agents` through the Control Plane.
The browser never receives direct Kubernetes, Hermes, Hindsight or provider
credentials/endpoints.

Reference dev URL:

```text
https://agents.dev.truxonline.com
```

The final UX is expected to move to SvelteKit without changing the
Portal -> Control Plane trust boundary.

### Control Plane MVP

The Phase 0 Control Plane is PostgreSQL-backed and provides the minimum vertical
slice needed for the POC:

- initializes a minimal platform schema;
- persists the POC `AgentIdentity` and `MemoryBank` mapping;
- initializes an OpenFGA store/model;
- lists authorized agents;
- proxies chat requests to the corresponding Hermes runtime;
- exposes an internal memory authorization decision endpoint;
- contains the initial usage-event table for later metering enrichment.

`POC_ALLOW_ANY_AUTHENTICATED=true` currently allows any authenticated Phase 0
pilot principal to use the seeded agent. This is an explicit bootstrap shortcut;
the OpenFGA path exists and must become authoritative before the POC expands
beyond the controlled pilot cohort.

### OpenFGA

OpenFGA is deployed in `indiba-system` from its upstream Helm chart and uses the
INDIBA PostgreSQL cluster. The initial model intentionally covers only the
minimum `user -> agent -> can_use` relationship required by Phase 0.

The complete tenant/group/repository/credential/memory relation model remains a
post-POC hardening deliverable.

### PostgreSQL

`indiba-postgresql` is a one-instance CloudNativePG cluster in `indiba-system`.
It currently hosts:

- `platform_core` for the Control Plane;
- `openfga` for OpenFGA.

Credentials are projected from OpenBao through External Secrets.

Hindsight uses a separate tenant-local `hindsight_indiba` PostgreSQL/pgvector
database in Phase 0. This intentionally exercises a separate memory credential
and database boundary.

### HermesRuntime and Operator

`HermesRuntime` (`agents.indiba.io/v1alpha1`) remains the runtime contract. The
dev overlay applies the Bertrand/Nadia reference CR and the MVP operator
reconciles it to:

- one always-on Hermes Deployment;
- one Service;
- one private AgentHome PVC;
- one per-runtime capability Secret;
- runtime status on the CR.

The operator validates the Phase 0 tenant identity before reconciliation.

### Hindsight memory

Hindsight 0.10.0 is deployed for the INDIBA tenant from the upstream OCI Helm
chart. It uses the dedicated `hindsight_indiba` pgvector database and sends its
LLM/embedding requests through the INDIBA LLM Gateway.

The stable internal abstraction is:

```text
hs-indiba.tenant-indiba.svc:8888
```

The service selector is pinned to the Hindsight API component generated by the
Helm release.

For Phase 0, bank authorization is enforced by an INDIBA Memory Gateway placed
between Hermes and Hindsight:

```text
Hermes capability
  -> Memory Gateway
  -> Control Plane authorizes (AgentIdentity, bank, operation)
  -> Hindsight
```

This lets the POC test negative cross-bank access immediately. The production
target remains Hindsight-native enforcement with `TenantExtension` +
`OperationValidatorExtension`; the Memory Gateway is intentionally replaceable.

### LLM Gateway

The MVP LLM Gateway accepts only the platform workload capability, injects the
OpenRouter credential projected from OpenBao, and streams the upstream response.
Hermes and Hindsight therefore do not receive the OpenRouter provider key.

Delegated OAuth/device-flow brokerage is not implemented yet. The production
model remains one principal/provider authorization reusable by authorized
AgentIdentity objects, with the Gateway as the unique refresh-token authority.

## Tenant boundary

Phase 0 has one tenant cell, `tenant-indiba`.

Isolation is layered:

1. `HermesRuntime` is namespaced;
2. Control Plane and Operator RBAC is bound only in `tenant-indiba`;
3. a Kyverno `Enforce` policy denies Phase 0 runtimes outside that namespace and
   requires `tenantRef=TEN00001` plus the matching immutable tenant UUID;
4. the Operator independently rejects a mismatched namespace/tenant identity;
5. namespaces use default-deny network policy;
6. memory bank access is independently authorized by the Memory Gateway/Control
   Plane path.

`tenant-indiba` temporarily enforces Pod Security `baseline` while auditing and
warning against `restricted`, because the current Hermes image has not yet been
qualified under a fully restricted startup contract. `restricted` remains the
production target.

## Security invariants

1. Kubernetes DNS/service discovery locates services; runtime IPs are never
   persisted as business configuration.
2. NetworkPolicy limits reachability but is never treated as authentication.
3. `bank_id`/`bankRef` is an identifier, not a credential.
4. Cross-bank retain/recall/reflect access must fail even when another bank ID is
   known.
5. Hermes workloads receive platform capabilities, not provider API keys.
6. Caller-supplied tenant/user/agent headers are never authoritative outside the
   trusted Portal/Control Plane path.
7. Runtime mutable state is isolated per AgentIdentity; writable homes or OAuth
   files are never shared between runtimes.

## Intentionally deferred after Phase 0

- NATS/JetStream, wake-up protocol and KEDA scale-to-zero for agents;
- generic session scheduler/concurrency model;
- full OpenFGA relation graph and force-allow/force-deny resolver semantics;
- delegated provider OAuth/device flow;
- direct Hindsight `TenantExtension` + `OperationValidatorExtension` package;
- CNPG-qualified pgvector database image/lifecycle for Hindsight;
- generic Python/browser execution environments and dynamic package policy;
- production HA, billing and multi-region operation.

## Build

```bash
kustomize build apps/60-services/indiba-platform/overlays/dev
```

The dev overlay includes the representative Bertrand/Nadia `HermesRuntime`, so a
working MVP operator materializes the always-on Hermes runtime after sync.
